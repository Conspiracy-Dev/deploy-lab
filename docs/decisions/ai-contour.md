# AI contour decisions

- **Canonical rules:** `AGENTS.md` is the tool-agnostic authority because Codex reads it natively and provider adapters must not become competing rule sources.
- **Cursor rules:** always-on and on-demand rules live in `.cursor/rules/` because it is Cursor's native, path-aware format, while Claude follows the router and Codex receives on-demand guidance as Skills.
- **Skills:** `.cursor/skills/` is canonical because Cursor also owns the native rule surface; `.claude/skills/` and `.agents/skills/` are physical checked copies so cloning works across operating systems without symlinks.
- **Provider capabilities:** Cursor has neither project subagents nor hooks, so the contour does not emulate them; Claude uses declarative agent files and `settings.json`, while Codex uses user-requested manual parallel fan-out and native `hooks.json`/`config.toml`.
- **Quality tooling:** Prettier, ESLint with TypeScript and complexity checks, Stylelint with standard CSS and Vue SFC rules, Knip, dependency-cruiser, Madge, Gitleaks, and Lefthook are used because each provides an established deterministic check for formatting, code quality, styles, unused surface, dependency direction/cycles, secrets, or Git gates.
- **Deliberate omissions:** no custom dead-code, cycle, secret, or formatting scripts are added because the selected mature tools already own those concerns; no database or UI-kit MCP is configured because the active project has no justified matching integration.
- **MCP synchronization:** `.mcp.json` is the JSON canonical source, `.cursor/mcp.json` is its checked copy, and `.codex/config.toml` translates the same justified server inventory into TOML because Codex does not consume the JSON format.
- **MCP scope:** Context7, browser, DevTools, and sequential planning are configured only for public library documentation, approved local-browser proof, inspection, and complex plans; private docs, sensitive internal origins, and remote service MCPs remain disconnected without an explicit need and approval.
- **Figma integration:** the official remote Figma MCP is project-scoped with OAuth and Codex `writes` approval because it reads authorised design data but can expose mutation tools; no Figma secrets, asset URLs, or copied vendor skills are stored in the contour.
- **Figma handoff:** the canonical DeployLab node URL is documented in the router and onboarding because agents need a stable read-only design target, while each Figma mutation still requires separately scoped owner approval.
- **Figma Code Connect:** Code Connect is deferred until DeployLab has stable reusable code components with agreed Figma mappings, because installing a publishing workflow without that source-of-truth pair adds dependency and drift without useful verification.
- **Repository delivery:** Commitlint with the Conventional preset runs in Lefthook `commit-msg` because commit-message syntax is a deterministic Git concern; `deploy-lab-git-delivery` is a checked-copy agent workflow for scope, evidence, and explicit commit/push authority rather than a second enforcement mechanism.
- **AI-first onboarding:** `pnpm setup` and `pnpm setup:doctor` are Node/Corepack orchestration because a clean clone must prove the same prerequisites on Windows, macOS, and Linux without global Git mutation or shell-specific setup instructions.
- **Task intake:** `deploy-lab-task-intake` is a manual, checked-copy Skill plus a small plan-shape CLI because ambiguous or high-impact work needs an explicit YAGNI boundary and evidence plan, while ordinary local edits must remain fast and direct.
- **Skill invocation guard:** `disable-model-invocation: true` remains in every checked-copy Skill because Claude requires it for the safety gate and Codex safely ignores unknown frontmatter; the documented Agnix exception preserves byte-identical mirrors rather than creating provider drift.
- **Local secret scanner:** the bootstrap downloads only the pinned official Gitleaks release after verifying the vendor's published SHA-256 because Gitleaks has no project-local Node distribution and a random package wrapper would weaken the trust boundary.
- **Module boundaries:** refactors follow an ownership seam, explicit public contract, dependency direction, and observable data flow rather than a line-count target, so a shorter file alone is never evidence of architectural improvement.
